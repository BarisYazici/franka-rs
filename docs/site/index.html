FR3 + Panda / Native Rust / Python ready / Apache-2.0

Your application here. Control beside the arm.

The core library, franka-rs, turns goals into smooth motion and communicates directly with the robot. No libfranka or C++ to install.

Want to work from your laptop? Put franka-node on a Pi 5. It runs the trajectory generator and impedance controller there. Zenoh is just the messaging layer carrying goals and state between your laptop and the Pi. The Pi talks to the robot over wired Ethernet. No separate Zenoh router is needed.

  • Your application sets the goal. A script, a policy, or a device integration sends position or joint targets.
  • The Pi runs the control algorithm. franka-node uses franka-rs to generate motion and calculate torque commands every millisecond.
  • Add peripherals when needed. Cameras and recording run alongside control. The core library also works on its own.

Get started

Choose where your application runs. The machine wired to a real robot needs Linux realtime setup. A laptop that talks to the Pi needs ordinary Python.

Rust Python Laptop + Pi Simulator

Rust, on the realtime host

In an existing Cargo project. Rust 1.89 or newer; the library is imported as franka. Build with --release: a debug build of a stiff torque controller misses cycles.

cargo add franka-rs

Next: installation details, realtime setup, then your first program.

Python, on the realtime host

Use Python 3.9 or newer in a virtual environment on the Linux realtime host. Rust runs the control loop underneath your Python program.

python -m pip install franka-rs
import franka
robot = franka.Robot("172.16.0.2")
print(robot.read_once().q)  # read joint positions; no motion

The wheel is franka-rs, the import name franka. Prepare the robot connection first, then follow the examples in From Python.

A laptop and a Raspberry Pi 5

On the laptop, use a Python virtual environment:

python -m pip install franka-node-client
import franka_node
with franka_node.Node("tcp/<pi-host>:7447") as node:
    print(node.status("pi"))  # node name from the Pi guide; no motion

On the Pi, a Raspberry Pi 5 with a PREEMPT_RT kernel, wired to the robot, with Rust installed:

cargo install franka-node --locked

Replace <pi-host> with your Pi’s address after starting the node. Use the node and the client of the same version. Configuration and the first motion: Raspberry Pi guide and Serve arms over Zenoh.

The simulator

Watch the robot move: start the desktop viewer →

Start the simulator with Docker on Linux. Then use a Rust or Python client with realtime checks off. No robot is needed.

docker run --rm --network host ghcr.io/barisyazici/franka-sim:1.1.7

In a second terminal, from a source checkout with Rust installed:

FRANKA_REALTIME=ignore cargo run --release --example echo_robot_state -- 127.0.0.1

One container at a time: the ports are fixed by the protocol. Python uses the same environment variable. A node uses realtime = "ignore" in its TOML configuration. Divergences from the real arm are listed in Without a robot.

Direct Python uses franka-rs (import franka). Remote Python uses franka-node-client (import franka_node). They are different packages.

What will you build?

Policies

Run your model on a GPU workstation and send its goals to the robot. The realtime host handles smooth target tracking between updates.

Questions

Which robots?

The Franka Research 3 (FCI v10) and the Franka Emika Robot, the Panda (FCI v5). One binary; the protocol version is negotiated when it connects. The published simulator image is an FR3.

Do I need a realtime kernel?

Wherever the 1 kHz loop runs, yes: a PREEMPT_RT kernel, an rtprio limit and a wired link. That is your machine for direct use, or the Pi for remote use. A laptop that only talks to a node needs nothing special. Against the simulator, realtime checks are simply turned off.

Is it a 1 kHz callback API too?

Yes. Write the loop as a callback, drive it with read_once and write_once, or let the crate run it and set targets from any thread. Target control is the recommended path for anything that is not a 1 kHz program.

How does it compare with libfranka?

Wire layouts, rate limiting, filtering and error text are checked against libfranka's sources. Measured side by side against the simulator, loop timing is the same and the model agrees to 1e-14. Figures and method: Compared with libfranka and Benchmarks.

What is not there yet?

A ros2_control hardware interface, the vacuum gripper and a published simulator image for the Panda. The impedance backend of target control, the default since 0.3.0, is not yet validated on an FR3. The node's gripper path is simulator-tested, and camera recording is tested with synthetic input. The changelog tracks each release.

Where is the code?

github.com/BarisYazici/franka-rs: the client, the Python bindings, franka-node, franka-cam, the flight recorder and the tests that run against the simulator in CI.
